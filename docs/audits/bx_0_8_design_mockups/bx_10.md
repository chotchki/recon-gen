# BX.10 — Composite-key opaque IDs in URLs

> **Cell:** BX.10 design mockup. URL-only fix (operator lock: "don't
> want this bleeding into the shape yaml"). Five directions below;
> recommendation at the end. Final pick stays with operator.

## Current state

From the pre-flight screenshots:

- **`url_chain_child.png`** — `/l2_shape/chain/CustomerInboundACH::CustomerInboundACHReturnNSF,CustomerInboundACHReturnStopPay/edit`
  renders the chain. Page title and h1 are just `CustomerInboundACH`
  (the parent half). The composite key is invisible on screen but
  fully baked into the URL — any rename of parent OR child rail
  invalidates the bookmark.
- **`url_account.png`** — single-key kind (`/l2_shape/account/gl-1010-cash-due-frb`).
  Renames the same way (id is the kebab slug), but ASCII-clean, short,
  no `::` / `,` chars in path. Bookmark survives until a rename.
- **`read_card_account.png`** / **`read_card_account_template.png`** —
  read cards for non-composite kinds. Title row is `<id> <display name> <role-badge>`.
  Edit + Delete buttons sit directly under the title.
- **`topnav_edit_account.png`** — the edit page chrome already carries
  the composite-key data: page `<title>` is `Edit account · gl-1010-cash-due-frb`;
  there's a sticky h1 "Edit account · gl-1010-cash-due-frb — Cash & Due From Federal Reserve"
  on the strip, with a `← back to Accounts` link below it. **The breadcrumb / title
  slot exists today** — directions just decide what to put in it once URLs
  go opaque.

The two affected kinds:

| Kind | Composite-key shape | Where it's built |
|---|---|---|
| `chain` | `<parent>::<sorted-children-csv>` | `_studio_editor_routes.py::_entity_id` L5249-5273 |
| `limit_schedule` | `<parent_role>::<rail>::<direction>` | same fn, L5269-5273 |

Same-fn `_find_entity_or_none` (L6219) does a linear scan over the
in-memory L2 list and matches on `_entity_id(kind, e) == entity_id`.
Any opaque-ID scheme has to round-trip through *something* this lookup
can dispatch on.

The four other kinds (`account` / `account_template` / `rail` / `transfer_template`)
already have single-string addressing keys; BX.10's scope is the two
composite-key kinds. Whether single-string kinds piggy-back is an open
question (§ open #2).

## Constraints from BX.0 / BX.0.7 locks

Citing the exact locks that bound the design space:

1. **Operator lock — URL only, YAML unchanged** (`bx_0_7_replan_with_triage.md`
   L91-99): *"deeper implied impact since the name is the id... don't
   want this bleeding into the shape yaml"*. Whatever we hash, the
   round-trip through the YAML loader must be identity. The L2 yaml
   continues to address chains by parent + children-list and
   limit_schedules by `(parent_role, rail, direction)`. **Mapping table
   lives in-memory at request time** (BX.0.7 same paragraph).
2. **Composite key stays in breadcrumb / title** (BX.0.7 L94-95): the
   operator-readable composite is the human-facing label *wherever it
   should be human-readable*. URL goes opaque; UI doesn't.
3. **Cold-read v1b motivation** (`bx_cold_read_v1b_author.md` L211):
   - **Rename fragility** — every URL pointing to a chain that references
     the old name breaks (bookmarks dead, audit links dead, links shared
     with the CFO dead).
   - **URL-encoding surprises** — `::` survives but spaces / `/` /
     non-ASCII don't round-trip cleanly through Slack pastes.
3. **CPA-readable banking terminology** (memory `project_design_north_stars`):
   the breadcrumb / title must speak the operator's vocabulary (e.g.
   `Customer Inbound ACH → NSF, StopPay`), NOT a synthetic ID prefix.
4. **No future-cleanup compat shims** (memory `feedback_no_compat_shims`):
   codebase is pre-stable. If the hash scheme changes, all in-flight
   bookmarks break; that's acceptable cost.
5. **Data-attribute anchors, not Tailwind classes** (memory
   `feedback_browser_drivers_user_facing_locators`): any new breadcrumb
   chrome carries `data-role="..."` for driver locators, not selector
   reliance on classes.
6. **Encode invariants in the type system** (memory
   `feedback_invariants_in_types`): the opaque-ID surface should be a
   `NewType` (similar to `SheetId` / `VisualId` in `common/ids.py`) so
   raw `str` round-trips at the boundary fail at the wiring site.
7. **Minimum table count, denormalize** (`project_design_north_stars`):
   the mapping is in-memory only — do NOT add a `chain_ids` table to
   the L2 cache.

## Directions

Five directions follow. Each:

- Names the hash scheme + breadcrumb shape + reverse-lookup pattern.
- Sketches the URL + breadcrumb chrome ASCII.
- Tradeoff matrix scored low / med / high (lower effort & risk better;
  higher mental-model fit, a11y, parity better).

### Direction A — Content-hash short ID (`h_a3f2e1`)

**Thesis.** Mint a stable 6-char base32 hash of the canonical composite
key (e.g. `sha256("CustomerInboundACH::CustomerInboundACHReturnNSF,CustomerInboundACHReturnStopPay")[:6]`).
Build a `{hash → entity}` map at L2-cache load time; URLs use only the
hash; breadcrumb / page title carry the composite key in human form
(`Customer Inbound ACH → NSF, StopPay`). When the composite changes
(rename), the hash changes, but the *old* URL is fundamentally about a
*now-deleted* entity anyway — return a clean 410 Gone page with a
"this chain was renamed; here's the current one if we can find it"
heuristic (substring match on parent name).

**URL shape:** `/l2_shape/chain/h_a3f2e1/edit`

**Breadcrumb / title sketch:**

```
┌─────────────────────────────────────────────────────────────────────┐
│ ← back to Chains                                                    │
│                                                                     │
│ Edit chain · Customer Inbound ACH → NSF, StopPay                    │
│              [data-role="composite-key"]                            │
│ h_a3f2e1   parent: CustomerInboundACH                               │
│ ↑ copy-id  children: NSF · StopPay                                  │
└─────────────────────────────────────────────────────────────────────┘
```

**Reverse lookup.** `L2InstanceCache` exposes a `chain_by_hash` /
`limit_schedule_by_hash` dict, rebuilt on every cache refresh
(symmetric with how `_entities_for_kind` reads). Hash → entity is O(1);
existing `_find_entity_or_none(kind, hash)` switches on kind: hash
kinds resolve through the dict, scalar kinds keep the linear scan.

**Tradeoff matrix.**

| Axis | Score | Notes |
|---|---|---|
| Effort | med | One new `NewType` (`OpaqueEntityId`); cache builds two dicts; one helper in `_entity_id`; 410-Gone page chrome. ~4-5h. |
| Risk | low-med | Hash collisions at 6 chars: ~1 in 16M; sasquatch has ~30 chains, 60-some limit_schedules. We're nowhere near birthday. Detect at cache build (`assert no collision`) and fail loud. |
| Mental model | med | Short hash is foreign on first sight; once operator copies the URL once they understand. **Crucially the breadcrumb is unambiguous** — no banker has to parse the hash. |
| Accessibility | high | Hash is a label; breadcrumb carries the semantic content. Screen readers read "Edit chain Customer Inbound ACH arrow NSF StopPay" — same as today's `<title>`. |
| Cross-renderer parity | high | App2 and QS-deep-link surfaces both need the same hash → entity lookup. One source of truth in `L2InstanceCache`. |

**Verdict notes.** Hash is unstable across renames — **this is fine**
because a renamed chain *is a different entity*. The 410 page makes
the stale-bookmark failure mode visible instead of silent.

### Direction B — Sequential row index (`r_017`)

**Thesis.** Assign a stable-per-cache-load sequence number to each
composite-key entity in declaration order. URLs use `r_<NNN>`; the
mapping is the position in the L2 yaml's `chains:` list. On rename,
the row keeps the same id (because it keeps the same position).
Trade-off: position is stable across renames, but NOT across YAML
reorderings — if the operator sorts the list, every bookmark dies.

**URL shape:** `/l2_shape/chain/r_017/edit`

**Breadcrumb / title sketch:**

```
┌─────────────────────────────────────────────────────────────────────┐
│ ← back to Chains                                                    │
│                                                                     │
│ Edit chain · Customer Inbound ACH → NSF, StopPay                    │
│ row 17 of 32                                                        │
└─────────────────────────────────────────────────────────────────────┘
```

**Reverse lookup.** Index into `instance.chains[017]`. Trivial.

**Tradeoff matrix.**

| Axis | Score | Notes |
|---|---|---|
| Effort | low | One-line resolver. ~2h. |
| Risk | high | YAML-list reorders break every bookmark. The cold-read explicitly called out "audit links need to be stable" — sort-by-name in any editor reorder breaks this. |
| Mental model | low | `r_017` is even more opaque than a hash, and the "row number" framing implies row order is meaningful — it isn't (chain order is operator-arbitrary in the YAML). |
| Accessibility | med | Same screen-reader story as A; index is just chrome. |
| Cross-renderer parity | high | Position is position. |

**Verdict notes.** Cheap but the failure mode is bad — a 30-second
operator action (re-sort the YAML) silently invalidates every bookmark.

### Direction C — Slug-of-parent + numeric disambiguator (`customer-inbound-ach-2`)

**Thesis.** Slugify the parent half of the composite (chain.parent /
limit_schedule.parent_role) to kebab-case, then suffix `-N` when N
entities share the same parent prefix. URL is readable AND survives
child renames (since only parent matters); breaks only on parent
rename. Half-opaque, half-readable.

**URL shape:** `/l2_shape/chain/customer-inbound-ach-1/edit`,
`/l2_shape/limit_schedule/customer-dda-customer-outbound-ach-1/edit`

**Breadcrumb / title sketch:**

```
┌─────────────────────────────────────────────────────────────────────┐
│ ← back to Chains                                                    │
│                                                                     │
│ Edit chain · Customer Inbound ACH → NSF, StopPay                    │
│ url: customer-inbound-ach-1                                         │
└─────────────────────────────────────────────────────────────────────┘
```

**Reverse lookup.** Slugify(parent) → list-of-entities → pick by `-N`
suffix. Slug computed at cache load; collision detection assigns the
disambiguator. Limit_schedule slug is `slug(parent_role) + "-" +
slug(rail)` to preserve the "many limit_schedules per role" cardinality.

**Tradeoff matrix.**

| Axis | Score | Notes |
|---|---|---|
| Effort | med-high | Slug fn + disambiguator allocation + collision tracking + parent-rename detection (the suffix can shift between two same-prefix entities when a third is added). ~6-7h. |
| Risk | high | "Half stable" is the worst kind. Operators *think* the URL means the parent and trust it; then renaming the parent rail (which they don't realize is the parent) silently moves the bookmark. The numeric suffix shifts when adding sibling chains — also silent. |
| Mental model | high (when it works) / low (when it breaks) | URL reads like banker vocabulary, which is great until it lies. Cold-read's concern was rename fragility; this scheme has subtle rename fragility. |
| Accessibility | high | Slug is readable. |
| Cross-renderer parity | med | Slug allocation depends on iteration order — App2 and the QS deep-link have to share the same iteration to keep slugs aligned. Fragile. |

**Verdict notes.** Looks great in screenshots, behaves badly under
multi-author edits and partial renames. Hybrid schemes that look
stable but aren't are the worst UX.

### Direction D — Encoded composite (URL-safe base64 of the composite key)

**Thesis.** Take the composite key verbatim and base64url-encode it
into the URL: `CustomerInboundACH::CustomerInboundACHReturnNSF,CustomerInboundACHReturnStopPay`
→ `Q3VzdG9tZXJJbmJvdW5kQUNIOjpDdXN0b21lcklu...`. The encoded form
round-trips losslessly back to the composite, then through
`_find_entity_or_none` unchanged. No mapping table needed (the URL IS
the lookup key). URL is hideous but the operator never has to read it
— breadcrumb still carries the human form.

**URL shape:** `/l2_shape/chain/Q3VzdG9tZXJJbmJvdW5kQUNIOjpDdXN0b21l.../edit`

**Breadcrumb / title sketch:**

```
┌─────────────────────────────────────────────────────────────────────┐
│ ← back to Chains                                                    │
│                                                                     │
│ Edit chain · Customer Inbound ACH → NSF, StopPay                    │
└─────────────────────────────────────────────────────────────────────┘
```

**Reverse lookup.** `base64url_decode(url_seg)` → composite key →
existing `_find_entity_or_none` path unchanged. Zero new state.

**Tradeoff matrix.**

| Axis | Score | Notes |
|---|---|---|
| Effort | low | ~1-2h. Just a codec + the breadcrumb chrome. |
| Risk | low-med | Same rename fragility as today (rename invalidates the encoded URL because it encodes the old name). URL length grows unboundedly with composite size (limit_schedules with long role names hit 100+ chars). Not as bad as `::,/` in the URL but still ugly. |
| Mental model | low | The URL is unreadable. The "copy URL into Slack" use case results in a 200-char block of base64. Doesn't fix the operator's complaint about ugly URLs — it just substitutes a different kind of ugly. |
| Accessibility | high | Breadcrumb still carries the semantic content. |
| Cross-renderer parity | high | Pure stateless codec. |

**Verdict notes.** Solves URL-encoding surprises (no `::` / `,` / `/`
in the path segment) but doesn't solve rename fragility or "audit
links rot". Operator's cold-read complaint was both, not just one.

### Direction E — Hybrid (content hash + human suffix, `h_a3f2e1__customer-inbound-ach`)

**Thesis.** Concatenate Direction A's content hash with a slug of the
parent. The hash is the lookup key (everything after the hash is
discarded by the resolver); the slug exists purely for human eyes
scanning the URL bar / a copied link in Slack. If the operator renames
the parent, the slug goes stale but lookup still works (hash carries
the actual addressing). This is the GitHub-issue-URL pattern (`/issues/42-add-foo-button`
where only `42` matters).

**URL shape:** `/l2_shape/chain/h_a3f2e1__customer-inbound-ach/edit`

**Breadcrumb / title sketch:**

```
┌─────────────────────────────────────────────────────────────────────┐
│ ← back to Chains                                                    │
│                                                                     │
│ Edit chain · Customer Inbound ACH → NSF, StopPay                    │
│              [data-role="composite-key"]                            │
│ h_a3f2e1   parent: CustomerInboundACH                               │
│ ↑ copy-id  children: NSF · StopPay                                  │
└─────────────────────────────────────────────────────────────────────┘
```

**Reverse lookup.** Split on `__`; take the leading `h_xxxxxx`; index
into the hash map. If the slug portion drifts from the entity's
current parent slug, optionally 301-redirect to the canonical form so
the bookmark self-heals on next visit. The 301-redirect is the GitHub
pattern.

**Tradeoff matrix.**

| Axis | Score | Notes |
|---|---|---|
| Effort | med | A's effort + slug rendering + 301-redirect when stale. ~5-6h. |
| Risk | low | Hash is the authority — slug drift is cosmetic only. Self-healing redirects keep the slug fresh. |
| Mental model | high | Operator pasting `/l2_shape/chain/h_a3f2e1__customer-inbound-ach/edit` into Slack: the slug tells the reader what the chain *is*; the hash makes it findable even after rename. Best of both worlds. |
| Accessibility | high | Same as A — breadcrumb carries semantic content. URL slug is bonus context. |
| Cross-renderer parity | high | Same hash table; slug is rendered identically by both. |

**Verdict notes.** This is the strongest direction for the
"audit/bookmark links sent to the CFO" use case that drove the
cold-read complaint, at moderate effort cost over A.

## Recommendation

- Comment: I agree with E

**Direction E (hybrid hash + human suffix).** Three reasons:

1. **Direct answer to the cold-read pain point.** The complaint was
   "audit links rot when we rename" + "URL-encoded composite keys are
   illegible in Slack pastes". E solves both: hash survives rename;
   slug makes the URL self-describing in copy/paste.
2. **Self-healing.** The 301-redirect on stale slug means the operator
   never has to manually fix a bookmark — copy-paste from Slack into
   the browser auto-canonicalizes to the current shape. This is
   exactly the GitHub-issues pattern operators already trust.
3. **Same lookup machinery as A.** The hash-only path (Direction A)
   and the hash+slug path (Direction E) share the same content-hash
   resolver + collision check — E is A plus a UI polish layer. If
   slug rendering proves operationally noisy, fall back to A by
   dropping the suffix; no data-shape rework.

Implementation order if E is picked:

1. `common/ids.py`: add `NewType("OpaqueEntityId", str)` with a
   construction-time validator (`h_<6 base32 chars>(__<slug>)?`).
2. `L2InstanceCache`: expose `chains_by_hash` + `limit_schedules_by_hash`
   dicts; computed at cache load with collision-detect assertion.
3. `_studio_editor_routes.py::_entity_id`: composite-key branches
   return the hash form; rename `_entity_id` → `_entity_addr` to keep
   the human-readable composite available as a separate helper for
   breadcrumb / title rendering.
4. `_render_read_card_header` + `_render_edit_page_header`: add the
   `data-role="composite-key"` strip below the title with parent +
   children rendered as banker vocabulary.
5. 301-redirect handler: when URL slug ≠ current canonical slug, 301
   to canonical.
6. 410-Gone handler for non-existent hash (deleted entity).
7. Drivers (`tests/e2e/_drivers/app2.py`): update navigation helpers
   to construct opaque URLs from `(kind, composite_key)` tuples; cell
   should expose a `addr_for_chain(parent, children)` test helper so
   tests don't hand-compute hashes.

Final pick stays with operator.

## Open questions

Items for operator review beyond direction choice:

1. **Hash length.** 6 chars (`h_a3f2e1`) gives ~1B addressable
   entities before birthday paradox at 0.1% collision. Sasquatch has
   < 100 composite-key entities; any midsize CU is unlikely to exceed
   500. **Open: should we go shorter (4 chars, `h_a3f2`) for prettier
   URLs at the cost of earlier collision risk?** The collision-detect
   assertion catches the failure at cache load (loud, not silent), so
   the risk is operator-visible not operator-burned.

   - Comment: 6 is better since the collison risk is way lower

2. **Should single-key kinds (`rail` / `transfer_template` / `account` /
   `account_template`) also opaque-ID?** The cold-read complaint is
   specifically about composite-key kinds, but operator renaming a
   rail also breaks the rail's URL. Three options: (a) leave single-key
   URLs as-is (cold-read's literal ask); (b) opaque everything for
   consistency (URL surface is uniform); (c) opaque single-key kinds
   only when the addressing string contains a non-ASCII char or
   exceeds N chars (heuristic; complicated). **Recommend (a)** — keep
   scope tight; revisit if the next cold-read flags rail-rename
   bookmark rot.

  - Comment: If there is a common helper, I'd rather be consistent than have split implementations.

3. **Stale-bookmark policy.** When a hash 404s (chain was deleted),
   should the 410 page attempt a fuzzy match ("the closest chain we
   can find is `Customer Inbound ACH → NSF, StopPay, Reject`")? Adds
   helpfulness but risks misleading. **Recommend no fuzzy match** —
   clean 410 with a list of all current chains the operator can scan,
   per the existing `_entity_gone_response` pattern.

  - Comment: Agree, no fuzzy.

4. **Breadcrumb composite-key visibility.** The mockups show
   `parent: CustomerInboundACH / children: NSF · StopPay` in a small
   strip below the title. Alternative: render only the human-readable
   `Customer Inbound ACH → NSF, StopPay` in the title and put the
   raw-composite form behind a [?] side-panel trigger (BTa.1 infra).
   **Open: belt-and-suspenders inline vs. tucked into side panel?**
   The cold-read persona is a CPA — they need the kebab/PascalCase
   raw form too because that's what they cross-reference with the
   YAML. Recommend inline strip (visible by default) for the two
   composite-key kinds.

  - Comment: I'd go sidebar, no CPA is editting the YAML, an integrator will be that low level.

5. **Copy-ID button.** Sketch shows a `↑ copy-id` affordance below
   the hash. Useful for "paste this into the audit log entry" but
   adds chrome. Open: ship in BX.10 or defer to a follow-up polish
   cell? Recommend ship — clipboard write is 10 LOC and the operator's
   use case (sharing the stable opaque ID with auditors / CFO) is the
   whole point of the phase.

  - Comment: Ditch this, not needed.
