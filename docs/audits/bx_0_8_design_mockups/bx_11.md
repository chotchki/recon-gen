# BX.11 — Account vs AccountTemplate 1:1-vs-1:N distinction

- Meta Comment: (also in bx_6) the split hides and important truth, out of accounts/account templates comes role which is what is really used everywhere. It may be far better to treat accounts and account templates in the editor as variants on roles, make role the grouping and similar to rails (1 vs 2) make the user choose 1:1 and 1:N on add. that gives us space to explain better.

Cell: BX.11 (BX.0.8 design mockup). Surface: home-page sections + the
two list/embed bodies + read cards for `account` and
`account_template`. Operator's anchor (cold-read v1b, §2,
`03_list_account.png`): *"This is showing that we're not saying that
accounts are DIFFERENT than templates (the 1:1 vs 1:N)."*

The two kinds carry the same vocabulary on the surface (role, scope,
parent_role, EOD balance, cadence, offset) but mean qualitatively
different things in the topology:

- **Account** = ONE materialized ledger row. The GL line on the CFO's
  trial balance. Lives at one `id`.
- **AccountTemplate** = a CLASS of accounts whose runtime instances
  come from `instance_id_template` / `instance_name_template` applied
  to the customer's per-row data at ETL time. Lives at a `role`; one
  template materializes N instances.

A consultant who can't tell those apart at-a-glance will declare
`AccountTemplate{role: CashDueFRB}` (wrong — there's one Fed account,
not N) or `Account{role: CustomerDDA}` (wrong — there are 50k of them).
Today the home page lists them in two identically-styled accordion
sections side-by-side with nothing surfacing the cardinality contract.

## Current state

Screenshots reviewed: `home.png`, `read_card_account.png`,
`read_card_account_template.png`, `url_account.png`.

- **Home `Accounts` section** (`home.png`) — accordion with 16 cards.
  Each card shows kebab id + display name + role badge + Edit/Delete.
  Header reads `Accounts (16)`. No prose, no cardinality cue. Sits
  ABOVE the `Account templates` section identical in chrome.
- **Home `Account templates` section** — collapsed in the screenshot;
  same accordion shell as Accounts, no differentiation. Header reads
  `Account templates (3)`.
- **Read card — Account** (`read_card_account.png`,
  `url_account.png`) — title is `<id> <display name> <role>`. `<dl>`
  body lists: ID, Display name, Description, Scope, Role, Parent role,
  Expected EOD balance, Business-day offset, Balance cadence. Nothing
  signals "this is the single materialized row."
- **Read card — AccountTemplate** (`read_card_account_template.png`)
  — title is JUST `<role>` (no id — templates have no id, they have a
  role + two templates). `<dl>` body lists: Role, Description, Scope,
  Parent role, Expected EOD balance, Business-day offset, Balance
  cadence, Instance ID template, Instance name template. Two
  template-only fields (`cust-{n:04d}-snb`, `SNB Customer #{n:04d}`)
  hint at the 1:N nature if you know what `{n}` is. Nothing in the
  card chrome flags "this materializes into N runtime rows."
- **Side-panel glossary** already has a `singleton` term
  (`_side_panel.py` line 127-132) defining the distinction in prose,
  but no inline trigger from either list page or either read card
  surfaces it.

The two surfaces are interchangeable-looking. The cardinality
contract is fully visible to someone who already knows where to look
(parent_role on Account is "—" because IT is the parent; `instance_*`
template fields on AccountTemplate). Neither is salient.

## Directions

### D1 — Section-header prose + count-shape annotation

**Thesis.** The minimum-touch fix. Re-word each home-page section's
summary so the cardinality contract reads in the chrome itself. The
Accounts section gets "GL accounts and singleton subledger
controls — one row per real-world account"; the Account templates
section gets "Patterns that fan out at ETL time — one row per
template, many runtime instances each." Counts evolve from
`Accounts (16)` to `Accounts (16 declared)` and `Account templates
(3 patterns → ~12 050 runtime instances)` where the second number
sums each template's instance count from the per-template
projection (read out of the seeded DB or fall back to just
`(3 patterns)` if no DB connection). Same chrome, more honest copy.

```
┌─ ▸ Accounts (16 declared)  [GL accounts — one row per real-world account]      [search]  + Add  ↗
└─ ▸ Account templates (3 patterns → ~12 050 runtime instances)
       [Patterns the ETL fans out — one row per template, many runtime instances each]
       [search]  + Add  ↗
```

| Axis | Rating |
|---|---|
| Effort | XS — copy-only in `_HOME_SECTIONS` + `_render_home_page`; ~10 LOC |
| Risk | XS — no new components, no test churn beyond updated label text |
| Mental-model fit | Medium — the prose lands the contract but only when the section is closed; an operator who opens Accounts loses the cue immediately |
| Accessibility | High — text-only, screen readers pick up the section description verbatim |
| Cross-renderer parity | N/A — Studio surface only; the dashboards never list L2 entities |

### D2 — Per-card cardinality badge (mirror the rail subtype badge)

**Thesis.** Promote the existing rail subtype / role badge pattern
(`bg-link-tint text-accent border border-accent/25`) and add a
`Singleton` / `Pattern · N instances` badge in the title row of every
card. The badge is the always-visible at-a-glance cue; the section
header stays as-is. Card titles for Accounts pick up a `Singleton`
badge (or "GL singleton" when scope=internal and parent_role is None);
template cards pick up `Pattern → ~4 016 instances` reading the count
from the materialized DB (or `Pattern` alone when no DB).

```
┌─ Accounts (16) ──────────────────────────────────────────────
│ ┌──────────────────────────────────────────────────────────┐
│ │ gl-1010-cash-due-frb  Cash & Due From Federal Reserve    │
│ │                       [CashDueFRB] [Singleton]    Edit · Delete
│ ├──────────────────────────────────────────────────────────┤
│ │ gl-2010-ach-orig-settlement  …  [Singleton]    Edit · Delete
│ └──────────────────────────────────────────────────────────┘
└──
┌─ Account templates (3) ──────────────────────────────────────
│ ┌──────────────────────────────────────────────────────────┐
│ │ CustomerDDA  [Pattern · ~4 016 instances]    Edit · Delete
│ ├──────────────────────────────────────────────────────────┤
│ │ MerchantDDA  [Pattern · ~140 instances]      Edit · Delete
│ └──────────────────────────────────────────────────────────┘
└──
```

| Axis | Rating |
|---|---|
| Effort | S — extends `_render_read_card_summary` badge slot; ~30 LOC + an instance-count helper that hits `<prefix>_transactions` (or just count distinct `account_id` per template_role) |
| Risk | S — the instance-count query is the only new failure mode; degrade gracefully to `Pattern` alone when DB unavailable. Live count adds a per-render DB hit per template card; cache at section-render time, not per card |
| Mental-model fit | High — badge sits exactly where the operator's eye lands, persists when the section is open, and the count gives the CFO sign-off number ("you have 4 016 customer DDAs declared") for free |
| Accessibility | High — badge is plain text inside a span with explicit `data-role="cardinality-cue"`; screen readers read it as `singleton` / `pattern, ~4 016 instances` |
| Cross-renderer parity | N/A — Studio only |

### D3 — Split visual columns (Singletons left, Patterns right)

**Thesis.** Re-layout the home page's account-related real estate from
two stacked accordions into a side-by-side two-column band labeled
**Singletons** (left) and **Patterns** (right). Headers read "GL +
control accounts — one row each" and "Templates — one row, many
instances." Card chrome is identical to today; the spatial separation
itself does the work. Drops `account` and `account_template` from
`_HOME_SECTIONS` and renders them as a custom dual-pane block at the
top of the page (above Rails / Transfer templates / etc.).

### D5 — Hybrid: section-header prose (D1) + card badge (D2) + read-card cardinality band (D4) — the layered "say it three times" pattern

**Thesis.** The cold-read found ONE complaint but every-surface
fragility is the real failure mode (close one section, click into one
card, take one screenshot — the cue has to survive each). Ship all
three weight-graduated cues:

1. **Section header (D1)** — prose annotation visible at the closed
   accordion state.
2. **Card badge (D2)** — `Singleton` / `Pattern · ~4 016 instances`
   on each card title, visible the moment the section opens.
3. **Read-card cardinality band (D4)** — the deep-detail prose
   inside the card body for the operator who clicks in.

Side-panel glossary `singleton` term gets an inline `[?]` trigger
on each section header so first-time operators can read the full
definition without leaving the page. (Wires up if BTa.1 has shipped
by the time BX.11 lands; otherwise the trigger is a plain anchor
to `#singleton` on a future glossary page — minimal cost.)

| Axis | Rating |
|---|---|
| Effort | M — D1 + D2 + D4 stacked. ~120-150 LOC across `_studio_routes.py` (header) + `_studio_editor_routes.py` (card badge + body band) + an `instance_count_by_role` helper (one query, cached on the cache layer's per-request lifecycle). The side-panel trigger is one more line if BTa.1 is up |
| Risk | M — touches three surfaces; each is small but they ALL need their own test (anchor + visible text); ~3 new e2e assertions + 3 new unit assertions on the rendered HTML. Decoupled so partial-revert is cheap |
| Mental-model fit | Highest — three independent reinforcement points means an operator can't accidentally miss the contract from any entry path (closed home, open home, drilled-in card) |
| Accessibility | High — every cue is text inside semantically-correct landmarks; badge gets `aria-label="Singleton"` / `aria-label="Pattern, approximately 4 016 instances"` |
| Cross-renderer parity | N/A — Studio only |

## Recommendation

**D5 (the layered hybrid).** Final call stays with operator.

Why:

- The cold-read finding is about an operator's surface-scan
  ergonomics, not a one-place vocabulary gap. Fixing it in one place
  leaves three other paths into the surface still equally
  confusing. The marginal cost from D2 → D5 is small (~70-100 LOC)
  and the failure mode of "I added the prose but the operator
  never clicked the closed section" is exactly the kind of
  whack-a-mole the BX phase exists to prevent.
- The instance-count helper is load-bearing for both D2 and D4; once
  it exists, exposing it in both surfaces is free. Skipping D4 would
  mean leaving real CFO-visible numbers (the "you have 4 016
  customer DDAs" that gets quoted in the sign-off) off the read
  card, where they're most useful.
- Plays into the existing badge vocabulary (rail subtype, account
  role) — operators have already learned to read the badge slot;
  this is one more variant.
- Falls back gracefully on no DB: badge degrades to `Pattern` (no
  count); read-card band drops the `Currently N rows` line; header
  prose unchanged. Studio-only-no-DB is a real mode (cfg without
  `demo_database_url`).

If the operator wants a smaller scope, **D1 + D2 (skip D4)** is the
80% solution. D1 alone is too thin — the closed-section cue
disappears the moment the operator opens the section.

## Open questions

1. **Instance count source.** Three candidates: (a) live query on
   `<prefix>_transactions` for `COUNT(DISTINCT account_id) WHERE
   account_type = '<template_role>'`; (b) live query on
   `<prefix>_daily_balances` for `COUNT(DISTINCT account_id) WHERE
   account_role = '<template_role> AND balance_date = MAX(...)`;
   (c) derived from the template's static `count` declaration in
   `_materialize_instances` (no DB hit). (a) is most truthful but
   ETL-dependent; (b) is most consistent with the CFO frame
   ("today's instances"); (c) is the fastest. Recommend (b) with
   fallback to "—" when no DB; operator weighs.
2. **`Singleton` vocabulary.** The side-panel glossary calls it
   `Singleton` (existing). Bankers might prefer `GL line` or
   `Ledger row`. Glossary term is the contract; if it changes, the
   badge text changes with it — small. Operator chooses what reads
   on the badge.
3. **Cardinality of the Account chrome when `parent_role` is set
   (subledger control accounts).** SasquatchPR's
   `MerchantDDAControl` is an Account with a parent_role pointing at
   another singleton — still 1:1, but conceptually "I'm the rollup
   over N children." Does the badge stay `Singleton` or shift to
   `Singleton · rollup`? Recommend stay `Singleton`; the
   `Parent role` row in the body already names the parent. Avoid
   inventing a third badge state.
4. **Per-template instance count freshness.** If the operator just
   added a new template and the ETL hasn't fanned out yet, the count
   reads `0`. Misleading? Recommend: `Pattern · awaiting first ETL`
   when count=0; `Pattern · ~N instances` otherwise. One extra
   conditional, no extra component.
5. **Section header prose for `account`** — "GL accounts and
   singleton subledger controls" reads OK on SasquatchPR but in a
   real bank's chart of accounts could be 200+ singletons. Worth
   a sanity check: how does the prose age at scale? Recommend the
   prose itself is cardinality-honest ("Singletons — one row per
   real-world account; 16 declared, 200 declared") so it scales by
   counting.
6. **Should the side-panel `singleton` glossary entry expand** to
   call out the AccountTemplate side explicitly? Today it mentions
   "AccountTemplate, in contrast, materializes N instances" but
   doesn't define the inverse `pattern` term. If we badge things
   `Pattern`, the glossary needs a `pattern` entry too. One-line add
   to `_side_panel.py::GLOSSARY`.
