## Why I stopped at CL.3

**CL.4 + CL.5 + CL.6 are co-dependent and touch the L1 invariant SQL surface.** Specifically:

- **CL.4** changes seed.py to emit balance rows only on activity-days for `sparse`-cadence accounts (current behavior emits every business day).
- **CL.5** rewrites the L1 drift / ledger-drift / overdraft matviews to use `LAST_VALUE(balance) IGNORE NULLS OVER (PARTITION BY account_id ORDER BY business_day)` so the matview reads the carry-forward effective balance instead of the raw row.
- **CL.6** adds a new `balance_cadence_gap` L1 invariant matview that fires only for `explicit_daily`-cadence accounts with missing rows.

**Risk:** if I land CL.4 without CL.5 in the same commit, every sparse-cadence account suddenly has missing rows the existing L1 matviews aren't equipped to handle. False drift firings would cascade through ~50 unit + integration tests AND the BV.3.3 dogfood walk. If I land CL.5 without CL.4, the carry-forward logic is correct but never exercised (rows are still dense).

The cleanest landing is **one commit covering CL.4 + CL.5 simultaneously**, with the locked seeds re-locked in CL.10 immediately after, and CL.6 + CL.7 + CL.8 in follow-up commits. But the SQL rewrite touches matview shapes that are baked into:

- `tests/data/_locked_seeds/*.sql` (regenerated by `recon-gen data lock`)
- `tests/data/_semantic_locks/*.json` (regenerated by re-emit)
- The BV.3.3 trainer dogfood walk (per-kind matview signature checks)

If the SQL rewrite has a subtle bug, the test cascade will be wide and the root cause hard to triage. That's why I want your eyes on the audit's §3 (worked SQL) and §5 (matview rewrite plan) BEFORE I land it.
